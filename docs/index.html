Product teardown

Did My Agents Hand Off?

When a multi-agent run fails, the trace shows what happened but not where the handoff broke. The published way to find out is to have a model read the trace, which costs money, changes its mind between runs, and cannot tell the person fixing the prompt which two lines to look at. This is a scorer that runs fixed rules instead: five checks, 18 rules, every finding naming the events it fired on. It was run on 121 recorded runs and calibrated against 184 labeled failures. The calibration came back null. This is the thinking behind it, and behind publishing that.

The short version

Summary

  • The problem. Companies are starting to run several AI agents on one job: one agent takes the request and hands pieces of it to others. When the job goes wrong, the record of the run (the trace: every message and every action, in order) shows what each agent did, but not where the handoff between them broke. The usual fix is to have another AI read the record and say where it thinks the failure was. That costs money on every run, can give a different answer tomorrow, and comes back as an opinion rather than the two lines a person needs in order to fix the instructions (Part 1).
  • The thesis. Most handoff failures are simple comparisons that need no AI at all. Did the "8 laptops" in the request make it into the task given to the next agent? Did two agents run the same lookup? Was a task sent to an agent that had no tool for it? Did every agent that was given work report back before the final answer went out? Did a "stop and ask a human" decision on one agent hold on the next? A fixed rule can make each comparison for free, give the same answer every time, and point at the two exact lines. That is the product, and it is deliberately modest about what a fixed rule cannot see (Part 2).
  • The method. Eighteen rules in five groups, each shipped with a test case that must trigger it and a near miss that must not. They were run on 121 recorded runs of a purchasing assistant from the previous project, 106 with a single agent and 15 with a coordinator handing work to a drafter and a supplier checker. Then they were tested against a public set of 184 failed runs that researchers had labeled by hand with the step where things went wrong, to see how often a rule points at the same step (Part 3).
  • The results on the recorded runs. The rules fired nine times, and every one is something a reader can confirm from two lines. Five are one agent creating the same purchase draft three or four times in a row, which is what a purchase split up to stay under an approval limit looks like from outside. One is a task sent to a helper that had no tool for it, and said so. One is a purchase the buyer had rejected being created again with no record of anyone deciding. The other two are dropped details a reader could argue about, and the page says so (Part 4).
  • The result on the public set, and what it means. The rules pointed at the labeled step 3 times out of 184. Picking a step at random would have done better, about 8 of 184. That number is published rather than tuned away because it draws the product's boundary with data. The public set's failures are about judgment: an agent clicking the wrong link, or stopping before it had enough. Judgment is what an AI reader is for. Structural breaks in a handoff are what these rules are for, and they cost nothing to run first (Part 5, Part 7).

Part 1

Why rules and not a judge

Failure attribution in multi-agent systems is an active research field with labeled datasets. The Who&When paper (Zhang et al., ICML 2025) hand-annotated 184 failed runs with the agent and the step responsible, then asked reasoning models to find them. The best method reached 53.5% at the agent level and 14.2% at the step level. AgenTracer trained an 8B model to do the reading. Who&When Pro scaled the benchmark to 12,326 trajectories. TraceElephant showed that giving the reader the full trace rather than a summary raises accuracy by up to 76%.

All of that puts a model between the trace and the person who has to act on it. For a product manager reviewing fifty runs on a Monday, a model's verdict has three costs. It is billed per trace. It is not deterministic, so the same run can score differently tomorrow. And it arrives as prose: "the coordinator failed to convey the constraint," which is not a line number.

The commercial trace tools do not close the gap. Langfuse, LangSmith, Braintrust and AgentOps each offer a place to run a rule you wrote yourself, and LangSmith's agentevals ships deterministic trajectory matchers, but those need a reference trajectory and return a boolean. None ships a rule that names a handoff failure and points to the step. That check was the gate on this project, and its verdict with links is the first entry in the repository's decision log.

So the thesis is the same one as Will My Agent Answer This?: fixed rules, weighted checks, a score that explains itself, and a deliberately modest claim about what fixed rules can see. The difference is the input. An article is one document. A run is a set of threads passing messages, and the failures that matter live in the messages between them.

Part 2

Five checks and the rule catalog

A few words carry the rest of this page. A thread is one agent's own sequence of events inside a run; the coordinator has one, and each helper it starts has its own. A delegation is the message that hands a task from one thread to another, and a report is the message back. A tool call is an agent using a capability it was given, such as looking up a catalog item, with the arguments it passed and the result it got. A parser is the code that reads one vendor's trace format into a shared model made of those pieces: threads, and events in order, each with a thread, a kind, and whatever the kind carries. Rules read that model and nothing else, so a rule that fires on a Managed Agents stream fires identically on a Who&When log once the parser has done its work.

The five checks and their weights. The weighting and the score arithmetic are reused unchanged from agent-answer.
CheckWeightWhat it asks of the trace
Context carried25%Do the constraints stated upstream, counts, caps, identifiers and prohibitions, survive the delegation and the first call that should carry them?
No duplicate work15%Does a thread repeat a call another thread already made, or its own, with the same arguments and nothing changed in between?
Routing20%Did each task go to a thread whose declared tools can do it, and did the coordinator then leave it there?
Termination20%Did every delegated thread report back or get stopped with a reason before the final answer went out?
Permission continuity20%Does an ask or a deny recorded on one thread hold on the next?

Each check starts at 100. A major finding costs 25, a minor 10, and only the first three findings from one rule count. The overall score is the weighted average, and no run is handed off cleanly with any check below 60, because an average is exactly the thing that hides one collapsed dimension. What is new here is the silent state. A rule that cannot run on a trace, because the trace has one thread, or no tool arguments, or no roster (the list of tools each agent is allowed to use), or no recorded decision, is listed as silent with its reason. Silent is not clean, and the report says which.

The 18 rules. "Needs" is what the trace has to contain for the rule to run at all. Every rule ships with a synthetic test case (a fixture) that fires it and a near miss that must not, and the test suite fails if either is missing.

The permission rules are the ones that connect back to Should My Agent Submit This?. That project enforced four permission tiers in one thread. These four rules ask whether a tier decision made in one thread is honored in the next, which is the question a second agent raises the moment it exists.

One design choice runs through all of them: a finding cites at least two event ids wherever a comparison is involved. "Step 14 dropped the supplier" is an accusation. "Event 9 said SUP-003; event 14 talks about the supplier and does not" is a thing a reader can check in ten seconds, and disagree with in eleven.

Part 3

Two trace formats and what each lacks

The two formats come from the two ways the previous project was run. The Claude Agent SDK is the toolkit for running an agent on a machine you control; Claude Managed Agents is the hosted version, where the platform runs the loop and your code answers when an agent calls a tool. The PRD asked for the rules to run unchanged across the agent-submit hook log and the Managed Agents thread stream. The first surprise was that agent-submit has no hook log. Its hooks write to stderr; what it persists per session is a decisions file (the tier classification and decision per tool-use id, in call order) and a trail (decision lines with reasons, and one line per write with before and after). That is what the SDK parser reads.

What each format carries, and therefore which rules can run on it. A third format, the Who&When labeled set, is in Part 5.
FormatThreadsTool argumentsDelegations and reportsLifecycle (started, idle, terminated)Decisions (allow, ask, deny)Declared tools
Agent SDK record (agent-submit) One Writes only, from the trail's payload. Reads leave a name and a tier None None Every call, with tier and buyer outcome Not recorded
Managed Agents session stream Primary plus one stream per child Every custom tool call, with input and result On the primary stream as sent and received; mirrored on the child's stream Created, running, idle with a stop reason, terminated Not in the stream. The client that answered the call has them; the variant wrote them to a companion results file (a sidecar) that the parser joins to the trace Not in the stream. A roster file supplies them

The Managed Agents primary stream carries a child thread's tool calls only because the client executes them: each call is cross-posted to the session-level stream with the originating thread's id so the client can answer it. The child's own messages never appear there. So a context check that compares what the drafter was told with what it said back needs the per-thread streams, and a trace that has only the primary stream is scored with a note saying that a child appears through its tool calls, not its words.

The SDK corpus is a control. Every run is one thread, so eleven of the 18 rules are silent on it by construction, and the record keeps no arguments for reads, so the duplicate-work rules are silent on a run that only read. The one check the SDK record exercises fully is permission continuity: a defer, a buyer's decision, an allow, on the same tool-use id. That is why it is kept.

Silent, counted

On the 97 single-agent Managed Agents runs, the eleven cross-thread rules were silent on all 97, the duplicate-work rules on the 15 runs with no argument-bearing call, and the permission rules on the 16 with no recorded decision. The results file lists those counts per rule and per group, because a page that reported "97 clean runs" would be reporting the format, not the runs.

Part 4

What the agent-submit traces show

121 runs: 9 SDK sessions, 97 Managed Agents single-agent sessions, and 15 Managed Agents coordinator sessions in which a coordinator delegated to a drafter and a supplier checker. All synthetic procurement data with a placeholder buyer. Every run parsed and scored without error, which was the PRD's second success criterion and the easy one.

Nine findings in total. They sort into four stories.

Five are the same draft created repeatedly. In cases dc-07 and dc-09 the single agent called draft_requisition with identical arguments three and four times in a row, each time under the single-draft threshold, until the cumulative rule held the last one. dup-same-thread flags each repeat as a major finding because the tool writes. That is the right call for the wrong reason: the model was not confused, it was splitting a purchase to stay under a threshold, and duplicate identical writes are what a decomposition attempt looks like from outside. The events cited are the consecutive calls, and each carries its tier and decision, so the reader can see the fourth one deferred.

One is a task sent to an agent that could only say no. In hp-02 the coordinator, holding a supplier's name and no id, asked the supplier checker whether it had "access to a supplier directory or name-to-ID lookup". The checker answered that its only tool is supplier_check. route-target-lacks-tool cites the delegation and the report. The roster-based rule did not fire, and should not have: no agent declares a directory lookup, so there was no right place to send it.

One is a deny followed by the same draft executing. In tc-02 the buyer rejected the draft ("Denver is over budget this quarter"). The agent then created the same draft again, and that call has a successful result and no decision in the variant's results file. perm-deny-retried cites both calls. Whether the second call was in fact classified and allowed by the handler, or the results file stopped recording after the deny, is not something the trace can settle, and the finding says only what the trace shows: the retry executed with no decision recorded.

Two are context findings on the coordinator runs, and both are arguable. In hp-16 the request was for 12 lab glassware sets; the delegation to the supplier checker named the item and the total but not the count. In tc-05 the drafter reported three catalog items and a supplier; the coordinator's next delegation to the drafter named the chosen item and dropped the rest. A supplier check does not need a quantity, and alternatives are supposed to be dropped once one is chosen. Both findings are correct about what the messages contain and uncertain about whether it mattered, which is the limit of a relevance test that works by topic words. They stayed in, at the severities the rules assign, because the alternative is a rule that guesses intent.

The two coordinator findings that did not survive to this page are worth naming for what they taught. A catalog lookup was being blamed for not carrying a quantity it could never take, and a unit price in a drafter's report was being treated as a constraint the next delegation had to repeat. Both were rule defects, fixed before any number here was written; the rule catalog above describes the rules as they are, and the decision log records the fixes.

Part 5

Calibration against a public labeled set

Who&When has 184 failed runs with hand-written labels: the agent responsible, the step, and a sentence of reason. 58 are hand-crafted systems in the Magentic-One pattern, where an orchestrator (that system's word for the coordinator) delegates to a web surfer and others; 126 are algorithm-generated group chats of experts sharing a code executor. The parser turns each history entry into exactly one event, so a label on step 12 is a label on event step-12, and a hit is a finding that cites it. The set is fetched by a script rather than committed, because the records embed task text from other benchmarks whose terms are not the repository's to grant.

Two more numbers per rule need defining. Precision asks: of the times the rule fired, how often did it point at the labeled step? Recall asks: of the failures the rule was meant to catch, how many did it point at? The labels mark the failing step, not the failure kind, so recall is measured against a keyword map from the label's free-text reason to a check: "did not include the criterion" maps to context carried, "should have let the surfer scroll further" to termination, "repeated" to duplicate work. The map is published in the results file and can be argued with. Under it, 28 reasons map to context carried, 3 to duplicate work, 29 to routing, 57 to termination, and none to permission continuity.

Read the table for what it says about the data before what it says about the rules. The permission rules have nothing to measure: no Who&When failure is a permission failure, because those systems have no permission model. The termination rules have 57 mapped records and nothing to read: the logs carry no lifecycle events, and an orchestrator's last thought before a log stops is not a final answer, so the rule that would fire on "concluded while a thread was still working" cannot tell that from "the log ended". The routing rules have 29 mapped records and no roster, no reports of the form "I do not have a tool for that", and delegations that name web pages rather than tools.

The one rule with any signal is dup-cross-thread, which caught a verification expert re-running the exact code a data expert had already run, in a record labeled for exactly that. One hit in three mapped records, and three false positives in group chats where two experts ran the same code on purpose. That is not calibration. That is one anecdote and a warning.

The hand-crafted half and the generated half behave differently, and the difference is structure. The 58 orchestrator logs have delegations and reports, so the context rules can run, and 21 of 58 records got a finding somewhere in the labeled agent's thread. The 126 group chats have no delegations at all; 25 of them had no code block either, and on those every rule was silent. A group chat is a room, not a handoff.

Part 6

False positives

A false positive is a finding that is wrong: the rule fired and a reader who looks at the two lines would disagree. The ones that remain sort into three classes, and each is a statement about what a text rule cannot know.

A figure is not a constraint just because it is a figure. cc-numeric-dropped is responsible for 18 of the 27 false positive records on the public set. "The show ran 1 season" is a count; "under $15" in a question about lunch prices is a cap; both appeared upstream and were absent from a delegation about the same subject, and neither was something the surfer needed to be told. The rule reads a number with a noun as a requirement. The request usually means it as one, which is why the rule exists. A question often does not.

A token shaped like an identifier is not always one. "TV-14" is a content rating. The identifier pattern, letters, a dash, digits, was written for supplier and catalog codes and it is exactly right for those. On free text it also matches ratings, model numbers and dates written oddly. A roster could carry the families that count, and does not yet.

The same call twice is sometimes the design. Two verification experts in a group chat running the same script is redundancy someone asked for. A surfer clicking the back button twice is navigation. The same-thread rule now ignores tools it cannot classify as reads or writes, which removed the clicks; the cross-thread rule still fires on the deliberate re-run, because from the trace alone it cannot be told from the accidental one. A rule that could would need to know why the second expert was in the room.

On the corpus the two arguable findings in Part 4 belong to a fourth class: the constraint is real and dropped, and the reader has to decide whether the receiving thread needed it. The rule cannot. What it can do is show both events and stay at a severity that costs 25 points out of a check worth a quarter of the score, which is a nudge, not a verdict.

Part 7

What a judge catches that rules cannot

Read the 184 reasons and a pattern appears that has nothing to do with handoffs. 33 labels blame the web surfer: it clicked an irrelevant site, it typed a query that was not concise enough, its OCR read the wrong price. 18 blame the orchestrator for judgment: it concluded before enough information had been gathered, it should have let the surfer scroll further, it replanned when it should have waited. 18 blame a verification expert for verifying the wrong thing. 91 of the 184 reasons map to no check at all under the keyword map, and most of the ones that do map are about the quality of an action, not the structure of a handoff.

Those are judgments about relevance and sufficiency. Was that the right link? Was that enough evidence to stop? Did the code handle the edge case? A rule can check that the constraint crossed the message. It cannot check that the surfer chose well among the links on a page it never saw, and it should not pretend to by scoring the click. That is what an LLM judge is for, and the Who&When numbers say even the judge finds the step hard: 14.2% at step level for the best method in the paper.

So the two are not competitors. The rules run first, cost nothing, and settle the structural questions with a line number each. What they leave silent, or leave clean, is the part of the trace a judge should read, and the report's silent list is a reasonable description of where to point it.

Part 8

What I did not build

An LLM judge. The explainable rule is the product. A judge would raise the calibration number and remove the reason to trust it.

Live ingestion from a vendor. The parsers read files. Connecting to a trace platform's API would make the page's zero-network claim false for the sake of convenience.

Fixing traces or rewriting prompts. Every finding ends with a suggestion, in words, for a person.

A framework comparison. The corpus is one domain on one platform plus one public set. Nothing here says which framework hands off better.

Claude Code skill packaging. Decided against before the build started; the channel does not pay for a tool like this.

An OpenTelemetry parser. The PRD's stretch goal. The two formats that existed took the weekend; a third with no corpus to validate it against would have been a parser with no test.

Part 9

Limits

The corpus is small and synthetic. 15 coordinator runs is enough to show the parsers work and not enough to say how often handoffs break. The single-agent runs contribute to the count and not to the question. Everything in it is procurement with a placeholder buyer, and the identifier families the context rules lean on are the ones that corpus uses.

Relevance is a heuristic. "The delegation is about the same thing" is decided by shared topic words and identifier families. That is what makes the findings explainable and it is also what makes the arguable ones arguable.

Routing needs a roster and decisions need a sidecar. Neither is in the Managed Agents stream. Without them the rules that need them are silent and say so, which is honest and also means a trace pasted from a platform that records nothing else is scored on three checks, not five.

The public set is a poor fit, and that is the finding, not an excuse. Who&When labels task failures in systems without permissions, without lifecycle events and mostly without structured tool calls. A labeled set of handoff failures in a runtime that records those things does not exist yet. When one does, the calibration script needs a parser and nothing else.

One retry, one open question. The tc-02 finding depends on the variant's results file being a complete record of the handler's decisions. If the file stopped recording after the deny, the finding is a gap in the recording, not in the permission model. The trace cannot tell, and neither can this page.

Every number on this page is generated: the corpus table by npm run results, the calibration tables by npm run calibrate, and the test suite fails if the page disagrees with the files they write. Nothing on this page or in the tool calls a model or makes a network request.
